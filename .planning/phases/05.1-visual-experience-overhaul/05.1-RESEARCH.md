## Summary

This phase transforms an already-functional game from a flat, utilitarian dark theme into a premium cinematic experience. The codebase is well-structured for this work: every component already has a paired `.module.css` file, CSS custom properties are cleanly centralized in `src/index.css`, and the reduced-motion guard is already globally applied. The refactor is purely additive — new CSS tokens, upgraded fill rules, new animation wrappers — nothing structural changes.

The primary technical concern is the Framer Motion version selection. The project uses React 19.2.4. Framer Motion's peer dependency for React 19 was only added in **11.13.5** (not 11.0.0 through 11.13.4). The context spec says "framer-motion 11.x" — this is achievable, but the exact version matters: install `framer-motion@^11.13.5` to get React 19 peer dep support while staying on the 11.x major. The current latest is 11.18.2 (verified from npm registry, 2026-03-25).

The second concern is the `useLocation` integration needed by Framer Motion `AnimatePresence` in App.jsx. `BrowserRouter` is already in use with declarative route mode. Wrapping the `<Routes>` outlet with `AnimatePresence` requires reading the current route key from `useLocation()` — this means `AnimatePresence` and its `key` prop must sit inside the `BrowserRouter` tree, not wrapping it. App.jsx currently has no nested component for location access; the plan must add a layout wrapper or inline the `useLocation` call correctly.

The third concern is the ambient gradient + glass-morphism combination. Glass-morphism (`backdrop-filter: blur()`) requires that the element behind the glass surface is not fully opaque from the perspective of the browser compositor. The fixed `ambientLayer` div provides exactly this — but only if page content uses `position: relative` and sits at a higher z-index. Any component that sets `background: var(--bg)` with full opacity on a wrapper will block the glass effect on its children unless the glass container is a sibling of (not nested inside) the opaque wrapper.

**Primary recommendation:** Install `framer-motion@^11.13.5`, add the `ambientLayer` as a fixed sibling in `App.jsx` before the router outlet, and treat the UI-SPEC as the authoritative implementation checklist — it already resolves all design decisions completely.

### Pattern 1: Ambient Layer Architecture

**What:** A single fixed `<div aria-hidden="true" className={styles.ambientLayer}>` placed as the first child inside App.jsx's root wrapper. All page content sits at `z-index: 1` or higher. The ambient layer is at `z-index: 0` and `pointer-events: none`.

**When to use:** Applies to the App-level wrapper only — not inside individual page components. Pages do not each add their own ambient layers.

**Implementation in App.jsx:**
```jsx
// Requires useLocation — must be inside BrowserRouter
import { BrowserRouter, Routes, Route, useLocation } from 'react-router-dom'
import { AnimatePresence } from 'framer-motion'

function AppRoutes() {
  const location = useLocation()
  return (
    <>
      <div aria-hidden="true" className="ambientLayer" />
      <AnimatePresence mode="wait">
        <Routes location={location} key={location.pathname}>
          <Route path="/" element={<Landing />} />
          <Route path="/host-setup/:sessionId" element={<HostSetup />} />
          <Route path="/host/:sessionId" element={<Host />} />
          <Route path="/play/:sessionId" element={<Play />} />
        </Routes>
      </AnimatePresence>
    </>
  )
}

function App() {
  return (
    <BrowserRouter>
      <AppRoutes />
    </BrowserRouter>
  )
}
```

**Why the split:** `useLocation()` requires a Router ancestor. The current App.jsx puts `BrowserRouter` at the top, so `useLocation` must be called inside a child component. The pattern above extracts `AppRoutes` as that child.

**Source:** Framer Motion AnimatePresence with React Router — documented pattern in Framer Motion docs and React Router docs (MEDIUM confidence — verified from training knowledge, consistent with how location-keyed AnimatePresence works).

### Pattern 2: Glass-Morphism Surface Recipe

**What:** A reusable CSS class pattern applied uniformly to all card/panel containers.

**When to use:** ScenarioCard `.card`, ConsequenceReveal container, ContentNote container, FrameworkProfile `.sectionCard` + `.conflictSection`, WorldStatePanel, VoteTally container, PlayerRoster card, Host endPanel + reflectionCard. NOT applied to full-page backgrounds (`.page` keeps solid `--bg`), input fields, or timer display.

**CSS recipe (from UI-SPEC):**
```css
.card {
  background: var(--glass-bg);              /* rgba(18, 18, 30, 0.65) */
  backdrop-filter: blur(var(--blur-glass)); /* 16px */
  -webkit-backdrop-filter: blur(var(--blur-glass));
  border: 1px solid var(--glass-border);   /* rgba(245,158,11, 0.18) */
  border-radius: 12px;
  box-shadow:
    0 4px 24px rgba(0, 0, 0, 0.4),
    inset 0 1px 0 rgba(255, 255, 255, 0.04);
}
```

**Critical constraint:** The ambient gradient layer behind the glass surface must be visible through the card's semi-transparent background for the glass effect to render correctly. If a parent wrapper has `background: var(--bg)` (solid `#0a0a14`), the backdrop-filter blurs the solid background — which is fine visually (it blurs the dark bg) but loses the warm glow bleed-through. The ambientLayer being `position: fixed` means it underpaints everything, so no page-level wrapping bg override can block it at the compositor level.

### Pattern 3: Framer Motion Page Transitions

**What:** Each top-level page component wraps its outermost element with `<motion.div>` using shared `pageVariants`.

**When to use:** Landing.jsx, HostSetup.jsx, Host.jsx, Play.jsx — all four page-level components.

**Shared variants (define once, import or repeat):**
```js
const pageVariants = {
  initial: { opacity: 0 },
  animate: { opacity: 1, transition: { duration: 0.4, ease: 'easeOut' } },
  exit:    { opacity: 0, transition: { duration: 0.25, ease: 'easeIn' } }
}
```

**Reduced motion handling:**
```js
import { motion, useReducedMotion } from 'framer-motion'

function Landing() {
  const shouldReduce = useReducedMotion()
  const variants = shouldReduce
    ? { initial: {}, animate: {}, exit: {} }
    : pageVariants
  return (
    <motion.div variants={variants} initial="initial" animate="animate" exit="exit">
      {/* page content */}
    </motion.div>
  )
}
```

### Pattern 4: Round Transition (Within Play.jsx)

**What:** Framer Motion `AnimatePresence` keyed on `session.current_round` wraps the game content area inside Play.jsx. When the round key changes, exit animation fires before enter.

**When to use:** Only in Play.jsx, only for the round content area — not for the outer page shell.

**Implementation approach:**
```jsx
<AnimatePresence mode="wait">
  <motion.div
    key={`round-${session.current_round}-${session.status}`}
    variants={roundTransition}
    initial="initial"
    animate="animate"
    exit="exit"
  >
    {/* scenario card or consequence reveal content */}
  </motion.div>
</AnimatePresence>
```

**Key note:** The key must include BOTH `current_round` and `status` to trigger the transition when the round closes (status changes from `active` to `round_complete`) — not only when the round number increments.

### Pattern 5: FrameworkProfile Stagger (Replaces CSS `animation-delay`)

**What:** Replace the four staggered `opacity: 0; animation: fadeUp ... forwards; animation-delay: Xms` rules in `FrameworkProfile.module.css` with Framer Motion parent `staggerChildren`.

**Current code to remove:** `.sectionCard`, `.conflictSection`, `.leastUsedSection`, `.choiceLog` all have `opacity: 0; animation: fadeUp 400ms ease forwards; animation-delay: 0/200/400/600ms`. These become `motion.div` children instead.

**Replacement:**
```js
const containerVariants = {
  hidden: {},
  show: { transition: { staggerChildren: 0.25 } }
}
const sectionVariants = {
  hidden:  { opacity: 0, y: 12 },
  show:    { opacity: 1, y: 0, transition: { duration: 0.5, ease: 'easeOut' } }
}
```

### Anti-Patterns to Avoid

- **Animating MeterBar fills with Framer Motion:** MeterBar fills update on every Supabase real-time event. Using `motion.div` for width changes here adds React reconciliation overhead on a high-frequency update path. Keep meter fill as pure CSS `transition: width 0.8s ease`.
- **Wrapping BrowserRouter with AnimatePresence:** AnimatePresence needs `useLocation` to key on route changes — calling `useLocation` outside BrowserRouter throws. Always call it inside a child component of BrowserRouter.
- **Applying glass-morphism to input fields:** Inputs need solid backgrounds for readability. The UI-SPEC explicitly excludes them: keep `background: var(--bg-surface)` on `.input` and `.reflectionTextarea`.
- **Writing `--atmosphere-warmth` to `:root`:** The atmosphere tint must be written as an inline CSS variable on a layout wrapper element — not on `:root` — because it changes dynamically with worldState and `:root` inline style writes are not composited by the browser the same way.
- **Using Inter 600 weight:** The typography system is two weights only: 400 and 700. Inter 600 is used in the current `FrameworkProfile` (`.frameworkName: font-weight: 600`) and `Landing.jsx` `.sectionHeading` — both must migrate to 700. Only request font-weight 400 and 700 from Google Fonts.

## Common Pitfalls

### Pitfall 1: Wrong framer-motion Version Breaks Peer Deps

**What goes wrong:** `npm install framer-motion@11` resolves to `11.0.0` which declares `react: '^18.0.0'` as a peer dep. With React 19.2.4 installed, npm prints peer dependency warnings and may refuse to install in strict environments.

**Why it happens:** The context spec says "11.x" without specifying a minimum patch. The React 19 peer dep was only added in 11.13.5.

**How to avoid:** Always install with `npm install framer-motion@^11.13.5` or `npm install framer-motion@11.18.2` (current latest 11.x, verified 2026-03-25).

**Warning signs:** `npm warn peer dep` messages referencing framer-motion and react during install.

### Pitfall 2: AnimatePresence useLocation Called Outside Router

**What goes wrong:** If `AnimatePresence` with `key={location.pathname}` is wired in `App.jsx` at the same level as `BrowserRouter`, calling `useLocation()` throws: "You should not call `useLocation()` outside a `<Router>`".

**Why it happens:** `BrowserRouter` is the provider — `useLocation` requires it as an ancestor, not a sibling.

**How to avoid:** Split App.jsx into `App` (renders `BrowserRouter`) and `AppRoutes` (child component that calls `useLocation` and renders `AnimatePresence` + `Routes`).

**Warning signs:** Runtime error in browser console during development.

### Pitfall 3: Glass-Morphism Invisible When Parent Background is Solid

**What goes wrong:** A component applies `backdrop-filter: blur(16px)` but the glass effect appears as a plain dark rectangle with no blur bleed-through.

**Why it happens:** The element being blurred by `backdrop-filter` is the rendered content directly behind the glass element in the stacking context. If a parent `div` has `background: #0a0a14` (fully opaque), the blur operates on solid black — visually indistinguishable from no blur.

**How to avoid:** The `ambientLayer` div is `position: fixed` which means it is always in the background of the entire viewport, underpainting everything regardless of parent stacking. Glass containers need only `position: relative` to sit above it. Do not add solid background colors to intermediate wrapper divs between the ambient layer and glass surfaces.

**Warning signs:** Glass card looks identical to a solid `--bg-surface` rectangle with no soft glow edge.

### Pitfall 4: Framer Motion Conflicts with CSS Reduced-Motion Guard

**What goes wrong:** The global `@media (prefers-reduced-motion: reduce)` rule in `index.css` sets `animation-duration: 0.01ms !important` — this kills CSS animations but does NOT affect Framer Motion's JS-driven animations. A user with reduced-motion preference still sees Framer Motion transitions.

**Why it happens:** Framer Motion uses JavaScript to drive animations, not CSS `animation` — the CSS media query cannot reach it.

**How to avoid:** Use `useReducedMotion()` from framer-motion in every component that uses motion. When `shouldReduce` is true, pass `{ duration: 0 }` as the transition or pass empty/instant variants.

**Warning signs:** Accessibility audit fails for `prefers-reduced-motion` even though the CSS guard is in place.

### Pitfall 5: Round Transition Key Doesn't Fire on Status Change

**What goes wrong:** The cinematic fade-through between rounds doesn't trigger when the host closes a round (status `active` → `round_complete`). Only triggers when the round number increments.

**Why it happens:** If the AnimatePresence key is only `session.current_round`, the key stays the same when status changes within the same round. The transition from scenario view to consequence reveal — which is the dramatic moment — is missed.

**How to avoid:** Key on both round and status: `key={`round-${session.current_round}-${session.status}`}`. This fires the transition at round close AND round advance.

**Warning signs:** Consequence reveal appears instantly without fade — no cinematic pause between choice and outcome.

### Pitfall 6: Google Fonts Weight Mismatch

**What goes wrong:** Google Fonts link only imports weight 400, but CSS specifies `font-weight: 700` — browser synthesizes the bold style (looks different from true Playfair Display 700, especially at 28px).

**Why it happens:** If the `<link>` in index.html only requests `Playfair+Display:wght@400`, weight 700 is not downloaded.

**How to avoid:** Request both weights explicitly:
```html
<link href="https://fonts.googleapis.com/css2?family=Inter:wght@400;700&family=Playfair+Display:wght@400;700&display=swap" rel="stylesheet">
```

**Warning signs:** Headings look slightly too thin or with differently-shaped glyphs compared to design reference.

### Pitfall 7: ambientLayer Interferes with Click Events

**What goes wrong:** Elements positioned behind page content receive click events — or alternatively, the ambient layer intercepts clicks meant for interactive elements.

**Why it happens:** If `pointer-events: none` is not set on the ambient layer, the fixed div is in the event target path.

**How to avoid:** The `.ambientLayer` class in index.css must always include `pointer-events: none`. This is in the UI-SPEC CSS snippet — do not omit it.

**Warning signs:** Buttons don't respond to clicks; cursor doesn't change on hover.

### Atmosphere tint (computed in a worldState-aware component)

```js
// Compute warmth from worldState (0.0 to 1.0)
const warmth = worldState
  ? (worldState.trust + worldState.courage + worldState.solidarity + worldState.awareness) / 400
  : 0.5

// Write as inline CSS var on the layout wrapper
<div style={{ '--atmosphere-warmth': warmth }}>
  {/* page content */}
</div>
```

The ambient layer uses `var(--atmosphere-warmth)` via a CSS `calc()` to blend between amber and cool tones. Since the actual interpolation happens in CSS using the custom property value, and the ambient layer is fixed/global, the inline style must be on a wrapper that is an ancestor of all content and a sibling/descendant relationship to the fixed ambient layer allows the CSS variable to cascade down. The fixed ambient layer itself does not receive the inline style — it reads from an ancestor via CSS variable inheritance.

1. **`worldState` availability in App.jsx for atmosphere tint**
   - What we know: `worldState` is a prop passed through `ConsequenceReveal` and `MeterBar` from their parent pages. It is not stored at the App level.
   - What's unclear: Which component or page is the right place to write `--atmosphere-warmth`? Play.jsx already has `session.world_state`. Host.jsx has it too. Landing and HostSetup do not have worldState.
   - Recommendation: Write `--atmosphere-warmth` as an inline style on the page-level wrapper inside each page that has worldState access (Play.jsx's `.page`, Host.jsx's root). For Landing and HostSetup, use neutral value (0.5). This avoids prop-drilling worldState up to App.jsx or adding a context layer the architecture doesn't currently need.

2. **`backdrop-filter` on Safari iOS for phone players**
   - What we know: The `-webkit-backdrop-filter` prefix is required for Safari. The UI-SPEC includes it. Safari on iOS 14+ supports backdrop-filter without prefix but including `-webkit-` does no harm.
   - What's unclear: Whether the glass effect has performance implications on older iOS devices (iPhone 8 era) at 375px viewport.
   - Recommendation: Include both prefix and standard. If performance issues appear on device testing, fall back to a higher opacity `--glass-bg` value (e.g., 0.85 instead of 0.65) which reduces the blur workload while preserving the dark aesthetic.
