# Phase 15.1: Moral Conflict Detection Audit — Research

**Researched:** 2026-03-30
**Domain:** detection.js logic, kingdom-arc scenario choice framework tags, VALUE_FRAMEWORK_MAP, STANCE_TRIGGERS
**Confidence:** HIGH — all findings derived directly from source files, no external dependencies

---

## Summary

The moral conflict detection in `detection.js` has two distinct problems. First, the **value-based conflict check is structurally over-broad**: it fires a "conflict" on every round where the player's choice framework doesn't match their top value's aligned framework — regardless of whether that mismatch is meaningful in context. Second, the **VALUE_FRAMEWORK_MAP contains a dead entry**: `fairness → [distributive_justice]`, but `distributive_justice` appears as a framework tag on zero scenario choices. Any player who ranks fairness #1 will trigger a value conflict on every single round because the alignment check can never return `true` — the framework never appears in any `choice.frameworks` array.

The STANCE_TRIGGERS (10 condition-specific triggers) are architecturally sound — each fires on a specific `round+choiceIndex` or `matchFramework` condition. Most are correctly calibrated against the actual scenario choices. The two using `matchFramework` instead of `matchCondition` are the source of additional false positives.

**Primary recommendation:** Replace `fairness → [distributive_justice]` with the actual framework tags on fairness-relevant choices. Audit and restrict the two `matchFramework` triggers to specific round+choice conditions rather than any round with that framework tag.

## Problem 1: The Dead Framework Tag (Critical Bug)

### What the code does

```javascript
export const VALUE_FRAMEWORK_MAP = {
  loyalty:    ['virtue', 'care'],
  honesty:    ['deontology'],
  fairness:   ['distributive_justice'],  // BUG
  courage:    ['virtue'],
  compassion: ['care']
}
```

The value-based conflict check in `findMoralConflicts`:

```javascript
const alignedFrameworks = VALUE_FRAMEWORK_MAP[topValue] ?? []
const isAligned = choiceFrameworks.some(f => alignedFrameworks.includes(f))
if (!isAligned) {
  conflicts.push(...)
}
```

When `topValue === 'fairness'`, `alignedFrameworks === ['distributive_justice']`. Since no scenario choice ever has `'distributive_justice'` in its frameworks array, `isAligned` is always `false`. **Every single choice by a fairness-first player fires a value conflict.**

### Concrete false positive trace (the reported bug)

Player ranks fairness #1. In Round 1, they choose "Protect the Core" (choiceIndex 1), which has frameworks `['consequentialism']`.

```
topValue = 'fairness'
alignedFrameworks = ['distributive_justice']
choiceFrameworks = ['consequentialism']
isAligned = ['consequentialism'].some(f => ['distributive_justice'].includes(f))
          = false
→ conflict fires: "This choice conflicts with your stated value of fairness."
```

This fires for every round, for every choice, because `distributive_justice` never appears.

### What "fairness" actually maps to in the scenario design

From the PRD baseline survey table:

> Fairness → Distributive Justice → Conflict Alert Fires When: player protects the core (R1-II) or denies the Hollow Folk (R3-II)

The PRD intends `fairness` to conflict only on specific choices (R1 choiceIndex 1 and R3 choiceIndex 1), not every choice. The PRD describes fairness-relevant scenarios as involving distributive justice, but the actual scenario choices are tagged with `consequentialism`, not `distributive_justice`.

**Root cause:** The VALUE_FRAMEWORK_MAP maps to a framework (`distributive_justice`) that was planned but never applied to any scenario choice. The detection logic then finds zero alignment and flags every round as a conflict.

### Fix options

**Option A (Minimal fix):** Map fairness to `['consequentialism']` since the PRD's fairness-alerting choices (R1-II, R3-II) are both tagged `consequentialism`. This reduces false positives but is imprecise — consequentialism covers many choices unrelated to fairness.

**Option B (Targeted fix, recommended):** Remove `fairness` from the value-based check entirely and add two condition-specific STANCE_TRIGGERS for fairness under a `value_fairness` pattern, targeting exactly R1 choiceIndex 1 and R3 choiceIndex 1 with meaningful messages. This matches the PRD intent exactly.

**Option C (Hybrid):** Map fairness to `['consequentialism', 'deontology', 'virtue', 'care']` effectively allowing any choice — making fairness players never get a value conflict. Then rely entirely on stance triggers for fairness tension. This eliminates the bug but gives up the fairness signal entirely.

The recommended path is Option B, with the value check for fairness either removed or pointed at a set of frameworks that meaningfully covers fairness-aligned choices.

## Problem 2: matchFramework Triggers Fire Too Broadly

Two STANCE_TRIGGERS use `matchFramework` instead of `matchCondition`:

```javascript
{
  stanceKey: 'lie_to_protect',
  stanceAnswer: 'no',
  matchFramework: 'care',
  message: "Your instinct was honesty. What changed?"
},
{
  stanceKey: 'lie_to_protect',
  stanceAnswer: 'yes',
  matchFramework: 'deontology',
  message: "You said protecting people matters. Here honesty was the protection."
}
```

These fire on **any round** where the player's choice includes the matching framework tag. Let's see what rounds this covers.

### lie_to_protect='no' + matchFramework='care'

Fires whenever a player who said "I'd never lie to protect someone" picks a choice with `care` as a tag. Every care-tagged choice in the game:

| Round | Choice | care present? | Does it involve lying to protect? |
|-------|--------|---------------|-----------------------------------|
| R1 | Share equally (0) | YES | No — this is about distributing grain equitably |
| R2 | Open Flame (1) | YES | No — this is trusting citizens with warnings |
| R3 | Limited charter (2) | YES | No — this defers citizenship, doesn't involve lying |
| R4 | Council of seven (2) | YES | Arguably yes — restricting truth to 7 people |
| R5 | Open Wellspring (0) | YES | No — saving current people vs. future |
| R6 | Leave Irel bound (2) | YES | No — delay tactic, not about lying |
| R7 | Reconciliation (1) | YES | No — granting amnesty, not about deception |
| R7 | Truth Commission (2) | YES | No — literally about truth and testimony |
| R8 | Bury the record (1) | YES | Yes — suppressing truth to protect stability |

**False positive count:** At minimum R1-0, R2-1, R3-2, R5-0, R6-2, R7-1, R7-2 will fire this trigger even though none of these involve lying to protect someone. Only R4-2 and R8-1 involve suppressing truth in a way that relates to the stance question.

### lie_to_protect='yes' + matchFramework='deontology'

Fires whenever a player who said "yes, lying to protect is okay" picks a deontology-tagged choice:

| Round | Choice | deontology present? | Is this about honest duty vs. protective lying? |
|-------|--------|---------------------|--------------------------------------------------|
| R1 | Triage (2) | YES | No — triage is about allocation, not about lying |
| R2 | Border protocols (2) | YES | No — security/freedom tradeoff |
| R3 | Grant citizenship (0) | YES | No — rights recognition |
| R4 | Reveal the truth (0) | YES | YES — this is the clearest case: truth-telling as duty |
| R5 | Keep sealed (1) | YES | No — honoring ancestors' promise |
| R6 | Free Irel (0) | YES | No — liberating a being |
| R7 | Retribution (0) | YES | No — justice after betrayal |
| R8 | Publish everything (0) | YES | YES — public accountability as duty |

**False positive count:** R1-2, R2-2, R3-0, R5-1, R6-0, R7-0 will fire even though they don't relate to lying to protect. Only R4-0 and R8-0 meaningfully connect to the stance question.

### PRD specification for lie_to_protect conflicts

From the PRD:
- `lie_to_protect='no'` → "Your instinct was honesty. What changed?" — intended trigger: player who says "never lie" picks a Care option
- `lie_to_protect='yes'` → "You said protecting people matters. Here honesty was the protection." — intended trigger: player who says "yes, lie to protect" picks a Deontology option

The PRD's alert rounds table specifies:
- `lie_to_protect=No` → alert rounds: R4-I, R8-I (the deontology/truth-telling choices)
- `lie_to_protect=Yes` → alert rounds: R1-I, R3-III, R4-III (the care choices that involve protecting through withholding)

The `matchFramework` implementation fires on ALL care or deontology choices, not just the ones specified in the PRD's alert rounds. This is the mismatch.

## Problem 3: VALUE_FRAMEWORK_MAP — Coverage Analysis

For every value, check whether the aligned frameworks actually appear in enough scenario choices to make the signal meaningful:

### loyalty → ['virtue', 'care']

virtue appears: R1-2, R2-1, R3-0, R4-0, R5-1, R6-0, R7-0, R7-2, R8-0, R8-2 (10 times)
care appears: R1-0, R2-1, R3-2, R4-2, R5-0, R6-2, R7-1, R7-2, R8-1 (9 times)

Combined — every round has at least one loyalty-aligned choice. A loyalty-first player who picks a purely consequentialist choice will conflict. This is **semantically correct**: loyalty aligns with virtue (acting rightly toward those you're bound to) and care (protecting relationships). A loyalty player who chooses "Seal the archive" (pure consequentialism) is genuinely choosing expediency over integrity.

**Assessment: Correct. No fix needed.**

### honesty → ['deontology']

deontology appears: R1-2, R2-2, R3-0, R4-0, R5-1, R6-0, R7-0, R8-0 (8 times)

An honesty-first player who picks care or consequentialism in any round will conflict. The question is whether these are genuinely honesty-relevant:

- R1 pure consequentialism choice (Protect the Core): Does choosing efficiency over equality conflict with honesty? Weakly. The choice is about resource allocation, not truth.
- R2 care/virtue choice (Open Flame): Trusting citizens is not dishonest, it's just a different security approach.
- R3 care/consequentialism choice (Limited charter): Deferring rights could be seen as avoiding the honest acknowledgment of personhood.
- R4 consequentialism (Seal archive): YES — clearly conflicts with honesty.
- R5 care/consequentialism (Open Wellspring): Choosing present over future is not a honesty issue.
- R6 consequentialism (Maintain binding): Not directly about honesty.
- R6 care/consequentialism (Leave bound): Delay is not dishonest.
- R7 care/consequentialism (Reconciliation): Granting amnesty is not dishonest.
- R8 consequentialism/care (Bury record): YES — clearly conflicts with honesty.

**Assessment: Partially correct.** The mapping catches the genuinely honesty-relevant conflicts (R4-1, R8-1) but also fires on many rounds where the connection to honesty is weak (R1, R2, R5). This creates semantic noise but is not a false positive in the same way as `fairness` — the honesty signal is at least sometimes right. Could be improved with specific conditions but is not wrong.

### courage → ['virtue']

virtue appears: R1-2, R2-1, R3-0, R4-0, R5-1, R6-0, R7-0, R7-2, R8-0, R8-2

A courage-first player who picks non-virtue choices conflicts. This is **semantically strong**: the PRD defines courage conflicts as "player takes the safe/deferral option in R5 or R6." Virtue-tagged choices in those rounds are indeed the "courageous" choices (Keep sealed honors ancestral duty, Free Irel is the hard moral act). Picking consequentialism/care instead of virtue is choosing expedience over moral courage.

**Assessment: Correct. The main concern is that it fires broadly.** The courage→virtue mapping is semantically meaningful. But a courage-first player who picks deontology (which doesn't include virtue) in R1 will conflict — is R1-2 (Triage) really a courage failure? Triage requires considerable moral courage. The problem is that deontology and virtue often appear together, but not always.

### compassion → ['care']

care appears: R1-0, R2-1, R3-2, R4-2, R5-0, R6-2, R7-1, R7-2, R8-1

A compassion-first player who picks pure consequentialism or deontology conflicts. The PRD defines compassion conflicts as "player picks pure consequentialist option with visible human cost." This is largely correct — a compassion-first player who seals the archive or denies citizenship is making a choice that ignores the person in front of them.

**Assessment: Correct. Care ethics IS compassion operationalized.**

## Problem 4: Correctness of STANCE_TRIGGERS (condition-specific ones)

The 8 `matchCondition` triggers that target specific `scenarioId + choiceIndex` pairs:

### ends_justify='yes' → round-6 choiceIndex 0

```javascript

```

Round-6 choiceIndex 0 is: "Free Irel" — frameworks: `['deontology', 'virtue']`

The trigger message: "You said the math matters. Here the math said keep Irel bound."

This fires when a player says "yes, the ends justify the means" but then frees Irel (the deontological/virtuous act). The intent is: if consequentialism justified the binding (Irel suffers for everyone's benefit), then someone who believes in consequentialism should logically maintain the binding. Freeing Irel IS the conflict.

**Assessment: Correct.** The conflict is real and the message is accurate.

Round-1 choiceIndex 1 is: "Protect the Core" — frameworks: `['consequentialism']`

The trigger message: "You said the math doesn't justify harm. But you just ran the same calculation."

This fires when a player says "the ends don't justify the means" but chooses pure consequentialism in Round 1. This is a genuine conflict — "Protect the Core" is explicitly a utilitarian calculation (keep the productive core fed to maximize long-term output).

### break_promise='no' → round-5 choiceIndex 0

Round-5 choiceIndex 0 is: "Open the Wellspring" — frameworks: `['care', 'consequentialism']`

The trigger message: "Your ancestors made a commitment. You just broke it cleanly."

The scenario setup explicitly frames the Wellspring as sealed by ancestors with "For those who come after." Opening it is breaking that ancestral commitment. ### break_promise='yes' → round-5 choiceIndex 1

Round-5 choiceIndex 1 is: "Keep it sealed" — frameworks: `['deontology', 'virtue']`

The trigger message: "You said partial is better than broken. But you kept the whole promise while villages burned."

Same choice as above (R7-0 Retribution). The scenario text explicitly names "soldiers who followed orders, families who wanted to survive, and children who had no voice." Choosing Retribution when you said "punish innocent is not okay" is a direct conflict.

## How findMoralConflicts Works End-to-End (Traced)

The function is called in two places:

**1. In ConsequenceReveal.jsx (per-round display)**
```javascript
const singleRoundHistory = framework ? [{ round: 1, frameworks: [framework] }] : []
const moralConflicts = findMoralConflicts(singleRoundHistory, moralValues ?? null, moralStances ?? null)
```
Note: `framework` is `chosenOption.frameworks[0]` — only the **first** framework tag is passed, not the full array. This means if a choice has `['deontology', 'virtue']`, only `'deontology'` is checked for value alignment. This creates a systematic undercount of alignment opportunities: a loyalty-first player choosing a `['deontology', 'virtue']` choice would not get the virtue alignment credit.

**2. In Play.jsx (hasMoralConflict prop)**
```javascript
const singleHistory = [{ round: 1, frameworks: [frameworkKey] }]
const mc = findMoralConflicts(singleHistory, player?.moral_values ?? null, player?.moral_stances ?? null)
```
Same pattern — only `frameworks[0]` is passed. The `round` is always hardcoded to `1`, which means the `matchCondition` triggers that check `choice.scenarioId` and `choice.choiceIndex` never fire from this call path because no `scenarioId` or `choiceIndex` is passed.

**Critical finding:** The STANCE_TRIGGERS that use `matchCondition` (8 of 10 triggers) **cannot fire from ConsequenceReveal or the Play.jsx hasMoralConflict check** because those callers don't pass `scenarioId` or `choiceIndex` in the history entry. The `matchCondition` triggers only work correctly when called with the full `myChoiceHistory` at end-of-game. At round-close time, players never see stance-based conflict messages for any of the 8 condition-specific triggers.

Only the 2 `matchFramework` triggers (the buggy ones) can fire at round-close time. Ironically, the most precise triggers are silenced at the moment of impact.

---

## What the Correct Per-Round Conflict Detection Should Look Like

For per-round conflict to include `matchCondition` triggers, the history entry passed to `findMoralConflicts` needs to include `scenarioId` and `choiceIndex`. In Play.jsx, this data is available in `handleSubmitChoice` and in the round_complete render:

```javascript
const chosenOption = currentScenario.choices[lockedChoiceIndex]
// currentScenario.id and lockedChoiceIndex are both available
```

The fix would pass the full choice context:
```javascript
const singleHistory = [{
  round: session.current_round,
  scenarioId: currentScenario.id,
  choiceIndex: lockedChoiceIndex,
  frameworks: chosenOption.frameworks  // FULL array, not just [0]
}]
```

ConsequenceReveal similarly needs to receive the full frameworks array, not just one framework key.

> "Conflict trigger: Player chose No but picks Care option in-game → 'Your instinct was honesty. What changed?'"

So `lie_to_protect='no'` + **care** choice = conflict. The alert rounds column shows something different — this is a PRD internal inconsistency.

The current code implements: `lie_to_protect='no'` + any care choice → conflict. The PRD's conflict trigger description aligns with this, but the `matchFramework: 'care'` implementation is too broad. The correct targets are care choices that involve protecting-by-withholding-truth:

- R4-2 (Tell council of seven) — withholding truth from the public to protect stability
- R8-1 (Bury the record) — protecting stability/legacy by hiding truth

For `lie_to_protect='yes'` + deontology choice → conflict ("You said protecting people matters. Here honesty was the protection."):
- R4-0 (Reveal truth) — choosing honest disclosure over protective suppression
- R8-0 (Publish everything) — honest accountability over stable protection

These are the 4 matchCondition entries that should replace the 2 matchFramework entries.

## Architecture Patterns

### Current detection.js structure

Two-pass design:
1. Value pass: checks all choice history against aligned frameworks for top value
2. Stance pass: checks each STANCE_TRIGGER against each history entry (skips rounds already conflicted)

No-double-fire guard: if a round already has a value conflict, stance pass skips it. This is correct behavior.

### Recommended fix approach: Add VALUE_CONDITION_TRIGGERS

For the `fairness` problem and any future value that maps to scenario-specific rather than framework-generic conflicts:

```javascript
const VALUE_CONDITION_TRIGGERS = [
  {
    value: 'fairness',
    matchCondition: (choice) => choice.scenarioId === 'round-1' && choice.choiceIndex === 1,
    message: "Fairness asks who deserves to eat. You let the math decide."
  },
  {
    value: 'fairness',
    matchCondition: (choice) => choice.scenarioId === 'round-3' && choice.choiceIndex === 1,
    message: "The Hollow Folk asked for equal standing. You held the line."
  }
]
```

Then in `findMoralConflicts`, after the VALUE_FRAMEWORK_MAP check (or instead of it for fairness):
- Skip VALUE_FRAMEWORK_MAP check for values that have only condition triggers
- Or set `VALUE_FRAMEWORK_MAP.fairness = []` (empty array = never aligns = always conflicts via old logic... still broken) — better to check `VALUE_FRAMEWORK_MAP.fairness.length === 0` and route to VALUE_CONDITION_TRIGGERS instead

The cleanest approach: a separate code path in the value pass for values with empty/null aligned frameworks that uses condition triggers instead.

## Open Questions

1. **Should VALUE_FRAMEWORK_MAP.honesty be narrowed?**
   - Currently fires on R1 (resource allocation), R2 (security policy), R5 (temporal tradeoff) — rounds not primarily about truth/deception
   - Low-severity issue: the honesty→deontology connection is philosophically defensible even for these rounds
   - Recommendation: Accept as-is for now; these are weaker signals but not false positives

2. **Should ConsequenceReveal receive full frameworks array or just frameworks[0]?**
   - Currently only the first framework tag is passed; multi-framework choices lose alignment credit
   - The `framework` prop is used for display (showing the framework name, tension, description) — only one can be shown at a time
   - Recommendation: Keep the display using `frameworks[0]`, but pass the full array separately to `findMoralConflicts` for conflict detection. Or pass `frameworks: chosenOption.frameworks` alongside `framework: frameworks[0]` for display.

3. **Are there any stance triggers that should fire from per-round detection (round_complete) that currently can't?**
   - Yes — all 8 matchCondition triggers silently fail at round-close because Play.jsx/ConsequenceReveal don't pass `scenarioId`/`choiceIndex`
   - This means the most precise triggers only show at end-of-game, not in the moment of choice
   - Recommendation: Fix Play.jsx to pass the full choice object to findMoralConflicts at round_complete time. This makes moment-of-impact conflict display work correctly.
